## 실행

Python 3.12, Streamlit 1.55.0, pandas 2.3.3에서 검증했습니다.

```sh
python3 -m pip install -r requirements.txt
python3 -m streamlit run settlement_v2.py --server.address 127.0.0.1
```

설정이 없으면 가상 자료 체험 모드로 시작합니다. 체험 모드는 세션별 임시 SQLite를 쓰며 실제 파일 업로드를 제공하지 않습니다. 브라우저를 닫거나 서버가 재시작되면 자료를 유지한다고 보장하지 않습니다.

로컬에서 실제 자료를 쓰려면 `.streamlit/secrets.toml`에 다음을 설정하세요. 실제 비밀번호나 DB 주소를 GitHub에 올리지 마세요.

```toml
SETTLEMENT_MODE = "local"
SETTLEMENT_PASSWORD = "16자_이상의_충분히_긴_개인_비밀번호"
SETTLEMENT_DATABASE_URL = "sqlite:///data/settlement.sqlite3"
```

로컬 서버는 `--server.address 127.0.0.1`로 실행합니다. 로그인 후 업로드와 저장이 가능합니다. SQLite 파일과 원본 엑셀은 암호화된 디스크에 보관하고 외부 백업도 확보하세요.

## 사용 흐름

1. **새 파일 정산**에서 은행·카드 파일을 함께 올립니다. XLSX, XLS, CSV를 지원합니다. CSV는 UTF-8 또는 CP949를 선택합니다. 암호화 엑셀은 먼저 로컬에서 암호를 해제해야 합니다.
2. 자료 종류, 계좌/카드 별칭, 시트, 제목 행, 거래일·내역·금액 열을 확인합니다. 금액은 입출금 별도, 양수 출금/음수 환불, 양수 입금/음수 출금 중 선택합니다. 카드 승인 취소가 양수+별도 상태 열로 제공되는 파일은 원본에서 취소를 음수 금액으로 정리해야 합니다. 앱이 취소 상태를 임의 추측하지 않습니다.
3. 정상 저장한 파일의 계좌별 열 매핑·시트·제목 행·금액 방식을 기억합니다. 다음 달에는 저장한 계좌를 선택하면 적용합니다. 형식이 바뀌면 다시 확인합니다. 한 파일에서 여러 시트를 가져올 때에는 파일을 시트별로 나누어 올립니다.
4. 미분류·규칙 충돌·처음 보는 거래·중복 후보만 먼저 검토합니다. 검색과 카테고리 필터를 조합한 뒤 일괄 분류할 수 있습니다. `확인 처리 (분류 유지)`는 추천 분류를 일괄 확인할 때 씁니다. 중복 후보의 포함 여부도 확인하세요.
5. **검토한 정산 저장**을 누릅니다. 금액·날짜 오류 행이나 미확인 거래가 있으면 저장을 막습니다. 제외하는 거래도 확인 체크가 필요합니다. 거래월은 파일의 실제 거래일에서 결정합니다.
6. **저장한 월정산**에서 검색·수정합니다. 표를 고치면 현재 수정값으로 지표를 바로 계산합니다. 저장은 명시적으로 누릅니다. 다른 창의 수정과 충돌하면 덮어쓰지 않습니다. 금액·거래일은 원본 보존을 위해 화면에서 변경하지 않습니다. 잘못 올린 행은 제외 처리하고 수정한 원본을 다시 업로드해 검토합니다.
7. **백업**에서 JSON을 내려받습니다. 원본 엑셀은 앱이 보관하지 않으므로 따로 보관하세요.

## 집계 기준

| 표시 | 계산 |
|---|---|
| 월정산 수입 | 포함된 사업 은행 입금. 판매채널 수수료 차감 후 정산 입금 사용 |
| 사업 지출 | 포함된 사업 은행 출금 + 카드 사용 − 카드 환불 |
| 최종 순수익 (월정산 기준) | 월정산 수입 − 사업 지출 |
| 은행 순현금 증감 | 포함된 은행 거래 전체의 입금 − 출금. 이체·대출·카드대금도 반영 |

‘최종 순수익’은 사용자의 운영상 표현이며, 재고·미수금·감가상각 등을 반영한 회계상 순이익을 뜻하지 않습니다. 앱에 같은 도움말을 표시합니다. 카드 지출은 사용일 기준입니다. 납부월과 사용월이 다르므로 월정산 잔여금은 통장 실제 잔액이 아닙니다. 세금 예비비를 임의로 차감하지 않습니다.

카드대금 납부, 계좌이체, 대출, 개인/제외는 사업 집계에서 제외하되 은행 흐름에는 남깁니다. 카드 사용 자료가 누락되면 카드대금 납부 제외가 지출 누락으로 이어지므로 양쪽 자료의 기간과 완전성을 확인하세요. 은행 내역만으로 자동 대사 완료를 주장하지 않습니다. 단순 ‘이체’라는 단어를 모두 내부이체로 처리하지 않습니다. 대출 원금과 이자가 합산되어 있으면 원본을 나누어 준비해야 합니다.

## 분류와 중복

- 확인한 분류는 거래명·계좌/카드·입출금 방향·금액으로 기억합니다. 사용자가 명시적으로 금액 무관 기억을 선택할 수도 있습니다. 충돌 규칙은 확인 대상으로 돌립니다.
- 네이버페이·카카오페이·토스페이 같은 공용 결제명은 기억된 규칙이 있어도 확인을 요구합니다. 같은 이름·같은 금액이어도 목적이 다를 수 있기 때문입니다.
- 첫 택배/광고/카드대금 추천도 사용자 확인을 받습니다. 거래처명을 폭넓게 추측해 자동 확정하지 않습니다.
- 같은 파일 내용+자료 종류+계좌+시트를 다시 저장하면 DB의 고유키가 차단합니다. 이름만 바꿔 재업로드해도 차단합니다.
- 다른 파일의 거래일·자료 종류·계좌·거래명·입출금액·승인번호가 같으면 중복 후보로 남기고 기본 제외합니다. 한 파일 안의 동일 거래도 두 행 모두 보존하고 확인을 받습니다. 정상 반복 결제라면 모두 포함할 수 있습니다. 날짜/거래명/승인번호가 바뀐 변형 파일의 중복까지 완벽히 감지하지는 못합니다.
- `classify(..., advisor=...)` 확장 지점이 있습니다. 현재 AI API 호출·비밀키·외부 전송은 없습니다. AI 추천은 자동 확정하지 않는 구조입니다.

## 저장소 선택과 배포

로컬 SQLite는 개인 PC에서 비용 없이 쓰기 좋습니다. Community Cloud는 로컬 파일 영속성을 보장하지 않으므로 운영은 Supabase 등 영속 PostgreSQL을 사용합니다. 공식 안내: https://docs.streamlit.io/develop/concepts/connections/connecting-to-data

클라우드는 `.streamlit/secrets.example.toml`을 참고해 `SETTLEMENT_MODE="cloud"`, 긴 비밀번호, TLS DB URL을 설정합니다. PostgreSQL 연결이 없으면 저장을 중단하며 SQLite로 자동 전환하지 않습니다. Supabase의 실제 연결 문자열과 요금제/백업 정책은 사용자 계정에서 확인해야 합니다. 비용이 드는 서비스를 자동 생성하지 않았습니다.

전용 DB 또는 전용 스키마에 필요한 테이블 생성/읽기/쓰기 권한만 부여한 서버용 DB 계정을 사용하세요. 브라우저에 DB 자격증명을 노출하지 않습니다. Supabase 브라우저 Data API에서 이 테이블들을 공개하지 마세요. DB는 Streamlit 서버에서만 연결하며 `psycopg`가 TLS로 접속합니다. 실제 배포 시 Cloud 앱 자체를 비공개로 설정하는 것을 권장합니다. 앱의 단일 공용 비밀번호는 조직별 사용자 관리나 강한 로그인 방어를 대체하지 않습니다.

데이터 저장은 `settlement_` 접두어를 가진 새 테이블만 사용합니다. 파일+거래+규칙+열 매핑+이력이 한 트랜잭션으로 저장됩니다. 수정은 버전 조건을 검사한 행 단위 UPDATE이며 전체 clear/delete는 없습니다. 기존 Google Sheets와의 자동 동기화는 제공하지 않습니다. 앱에서 조회하는 월만 거래를 읽고, 신규 업로드의 중복 검사는 기존 거래와 대조합니다.

현재 앱을 계속 쓰면서 검증하려면 별도 Streamlit 앱으로 동일 저장소의 검토 브랜치와 `settlement_v2.py`를 연결합니다. 기존 `main/app.py` 연결은 유지합니다. 운영 전 다음 체크리스트를 완료하세요.

## 실제 자료 백업·전환 계획

1. 기존 앱 입력을 잠시 멈추고 `settlement_db` 전체 문서를 XLSX로 다운로드합니다. raw_data/mapping 외 탭도 보관하세요. 원본 월별 은행·카드 파일, 기존 코드 커밋, 배포 연결과 Secrets의 안전한 개인 사본도 확보합니다. **코드 백업과 실제 자료 백업은 다릅니다. 현재 실제 자료 백업은 미실시 상태입니다.**
2. 추가로 읽기 전용 도구를 사용할 수 있습니다. 아래 도구는 기존 시트에 쓰지 않으며 출력 파일이 있으면 덮어쓰지 않습니다. 서비스 계정 키는 기존 키를 로컬의 안전한 경로에 두고 사용하세요. 채팅이나 저장소로 전송하지 마세요.

```sh
python3 tools/backup_legacy.py --credentials /안전한경로/기존키.json --sheet-id 문서ID --output /안전한경로/정산시트-backup.json
```

3. 두 백업을 열어 탭별 행수, report_name별 건수, 입금/지출 합계, mapping 쌍을 원본과 대조합니다. 백업 시점의 동시 입력은 중단되어야 합니다. 도구는 행별 문자열을 보존하지만 시트 서식·수식·첨부파일까지 보존하는 전체 Drive 백업은 아닙니다. XLSX 사본도 함께 보관합니다.
4. **사용자 확인 후** 별도 PostgreSQL 시험 저장소에 대표 월 1~2개를 업로드합니다. 먼저 실제 원본 엑셀에서 거래일을 복원합니다. 기존 raw_data의 `date`는 저장일이어서 거래일로 이관하면 안 됩니다. 원본이 없는 과거 정산은 기존 앱에서 보관하고, 날짜를 임의 추정해 자동 이관하지 않습니다. 기존 mapping은 참고 후보로 검토하며 무조건 확정 규칙으로 복사하지 않습니다.
5. 은행/카드 원본별 건수·금액, 제외한 카드대금, 이체/대출, 개인지출, 환불, 반복결제 후보를 대조합니다. 새 지표와 구 지표의 차이는 항목별 근거로 설명되어야 합니다. 구 앱은 기본 세금 예비비 차감이 있으므로 같은 합계가 반드시 나오지는 않습니다.
6. 저장 후 재접속, 서버 재시작, 동시 수정, JSON 백업/별도 복원, DB 연결 실패를 시험합니다. PostgreSQL 실연결 검증과 실제 은행/카드 형식 검증은 아직 수행하지 않았습니다.
7. 시험 결과와 실제 백업 확인 후 사용자 승인을 받아 운영 연결을 전환합니다. 이전 앱과 시트는 삭제하지 않고 읽기 보관합니다. 문제 시 구 앱으로 복귀합니다. 전환 후에는 두 앱에서 같은 월을 동시에 수정하지 않습니다. 새 자료는 새 DB에서 별도 보존합니다.

## 백업 복원

JSON 백업을 **새 로컬 DB 파일**로만 복원하는 도구가 있습니다. 기존 DB에는 덮어쓰지 않습니다.

```sh
python3 tools/restore_backup.py settlement-backup.json data/recovery-new.sqlite3
```

복원 후 별도 로컬 실행에서 `SETTLEMENT_DATABASE_URL`을 새 파일 경로로 지정해 검증합니다. PostgreSQL의 운영 백업은 공급자 자동 백업/스냅샷과 별도로 관리하세요. JSON은 표준 필드와 수정 이력의 이식 가능한 보조 백업입니다. 운영 PostgreSQL 덮어쓰기 복원이나 기존 Sheets 이관 도구는 의도적으로 실행하지 않았습니다.

## 테스트

```sh
python3 -m unittest discover -s tests -v
```

테스트는 가상 자료만 사용합니다. 통화/날짜/엑셀 파싱, 카드환불, 중복 후보 보존, 카드대금·대출·이체 제외, 분류 충돌, 규칙 비활성화, 저장 원자성·중복 방지·낙관적 동시 수정 제어, 백업 복원, Streamlit 편집 지표·일괄 검토·저장·재조회, 미설정 운영 접근 차단을 검사합니다.
